# 项目一具体知识与操作

学习顺序是先运行、再看 DOM 与规则，最后做一次小范围验证。无需逐段标注全部网页。

## 1．DOM 是树，XPath 是查询

HTML 标签形成父子与兄弟关系。浏览器“检查”中看到的 class 或 id 是节点属性，不是正文正确性的标签；检查工具能展示结构，但不会自动替你决定哪些内容是文章。

阅读新闻抽取器，找到正文容器 XPath：

~~~python
bodies = tree.xpath("//div[@id='artibody']")
~~~

双斜杠 // 表示从查询上下文的后代中查找；[@id='artibody'] 是属性谓词；xpath 返回列表。因此要检查容器数量，不能不加验证就取 [0]。

把“应找到1个容器”写成显式条件，能够暴露改版或布局不匹配。否则一个匹配失败可能被误解成“文章没有正文”。

## 2．class 应按词匹配

一个标签可以同时有多个 class，例如 class="left_zw article-body"。@class='left_zw' 会漏掉这个节点，而 contains(@class,'left_zw') 又可能误匹配 left_zw_backup。

现有规则采用：

~~~xpath
//div[contains(concat(' ', normalize-space(@class), ' '), ' left_zw ')]
~~~

normalize-space 规范空白，concat 在两侧补空格，再匹配完整 class 词。学习操作：在规则中找出同样写法，解释为什么两端空格不能删。

## 3．./p 与 .//p 为什么不同

- ./p：当前节点的直接子段落。
- .//p：当前节点的所有后代段落。

直接子段落可能漏掉 section、details 或其他 div 内的正文；所有后代段落又可能进入广告或互动组件。不存在始终正确的一条选择器，需要结合容器和排除结构。

运行 batch 后，选一篇新闻看正文块的 XPath。检查是否出现嵌套结构、图说和表格，再去规则中找对应处理分支。

## 4．text_content 与 /text()

元素的正文可能跨多个内联标签，例如：

~~~html
<p>详情见<a href="/report">试点报告</a>，数据仍需核实。</p>
~~~

只取 node.text 或 ./text() 容易丢链接中的字或子节点后的 tail。text_content() 可以取得元素内的后代文字，再用空白规范化形成可读文本。

但不能对整个网页直接 text_content() 就当正文：那会把导航、侧栏和评论一起带入。先定位范围，再读取文字。

## 5．署名、采访问题、图说要分别处理

- “中新网记者 张三”：独立署名可归 author。
- “中新社记者：您如何评价……”：记者提问属于访谈正文，应保留。
- 图下的 pictext 或 figcaption：保留为 caption，而不是广告或独立作者。

规则中的 re.fullmatch 是整行匹配，适合限制独立署名的形状；仅用包含“记者”的判断会误删采访内容。学习操作：在抽取结果中找到 author 和 caption，回到规则解释它们由哪条条件产生。

## 6．为什么保留 excluded 与 warnings

excluded 记录明确移除的内容与位置，方便解释为何消失、恢复误删。warnings 记录抽取能力边界，例如图片像素没有解析。

发现图像时加警告，不等于已经判定图片内没有正文。没有证据时保持未知，比将缺失默认为正确更适合后续质量评估。

## 7．回归检查与质量评估的区别

回归检查回答“这次改动让固定样例发生了什么变化”；质量评估回答“这些变化符合任务要求吗”。

输出字段正确、XPath有效、文字来自原文，都不能证明正文完整。例如漏掉整个表格，剩余段落仍可能全部有正确原文位置。

亲手操作：

~~~powershell
.\.venv\Scripts\python.exe -X utf8 .\app.py batch
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests
Start-Process ".\reports\index.html"
~~~

在报告中只检查三处：文章最后一段是否保留、一个图说或小标题是否保留、一条明确推广或作者是否归位。检查的是已知样例，不要把这次观察当全网质量结论。

## 8．外部基线与人工金标的区别

当规则结果很难仅靠肉眼判断时，可以拿一个已经存在的传统正文提取器作为独立参照。本项目使用 Trafilatura 2.3.1：

~~~powershell
.\.venv\Scripts\python.exe -X utf8 .\app.py baseline
~~~

它会对15页本地 HTML 分别运行规则抽取和 Trafilatura，保存两边文本，再计算字符 5-gram 精确率、召回率和 F1。报告中的“需核查”只表示两边差异较大，不表示我们的结果错了。真正的判断顺序应是：

1. 看原 HTML 中这段文字属于正文、目录、相关推荐还是导航。
2. 看我们的模板规则为什么保留或排除它。
3. 看 Trafilatura 独有片段和我们的独有片段，而不是只看一个总分。
4. 决定是否符合页面类型和抽取目标，再决定是否修改规则。

一个具体例子是 `pydoc_library_index`：Trafilatura只输出5段导语，我们的规则输出39个块，其中包括标准库目录。F1只有0.149，但这里的目录是页面主要内容，不能为了让分数升高就删掉。反过来，新浪和中新网样例的基线结果带有推荐新闻或责任编辑，也不能把基线自动当成正确答案。

这项练习最重要的收获是：外部基线能告诉我们“差异在哪里”，不能告诉我们“谁是对的”。可复现对照、原始 HTML 和明确口径必须放在一起，才有评测价值。

## 9．这与岗位工作的关系

离线正文提取需要把同布局网页的规律写成可复用代码，再在 CPU 上批量执行。你在本项目应能解释：

1. 为什么选这个容器，容器可能漏掉什么或混入什么？
2. 为什么不能只按站点名或文件名选择抽取逻辑？
3. 为什么需要原文 XPath、原始 HTML 和版本/哈希？
4. 一条规则修复后怎样证明旧页面没有退化？
5. 工程通过、文字完整与真实业务效果分别有什么证据？

这些理解比背出几个 XPath 更能体现实际网页数据处理经验。
